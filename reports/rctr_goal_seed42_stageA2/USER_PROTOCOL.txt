结论：最新 RCTR Stage A 实验确实存在过度严格的问题，但主要不在数值精度，而在于把“精确复现历史演示”设成了“验证反事实控制机制”的必要前提。现有结果表明状态恢复技术取得了实质进展，尚不能据此否定 RCTR；我建议保留严格的可重复性检查，但重新设计算法准入条件。

## 一、最新实验到底失败在哪里？

状态恢复准入未通过，算法尚未测试

最新结果与最初的失败已经有明显区别。

| 检查项目                 | 最新结果                         | 判断   |
| -------------------- | ---------------------------- | ---- |
| HDF5 状态与观察索引         | 已确认存在一步偏移并正确对齐               | 通过   |
| 相同完整快照的重复执行          | 三个固定测试起点误差为 0                | 通过   |
| MuJoCo 2.3.5 的目标一步复现 | 三个 demo 误差均约 \\(10^{-14}\\)  | 通过   |
| 历史 8 帧转移复现           | 三个 demo 最大误差约 \\(10^{-12}\\) | 通过   |
| demo_2 下一步继续执行       | 状态误差 0.03313                 | 未通过  |
| GMM 分支与闭环恢复验证        | 0/54 条执行                     | 尚未开始 |
| RCTR 训练              | 0 次优化器更新                     | 尚未开始 |

表中状态误差是混合物理量的最大坐标绝对差，不能解释为米或弧度。

这意味着最新实验已经证明了两个重要事实：

第一，完整状态快照在当前测试条件下可以精确恢复并重复执行。

第二，旧 HDF5 演示中的完整历史控制过程，仍不能保证被重新复现。

这两者不是同一个问题。

## 二、为什么仍然失败？

### 原因 1：MuJoCo 版本差异确实影响了物理行为

实验对比了 MuJoCo 3.2.3 和 2.3.5。

目标一步转移误差：两个 MuJoCo 版本

最大状态坐标绝对差，使用对数刻度便于展示数量级差异；并非机器人位置误差。

报告还发现，同一 XML 在两个版本编译后，部分物体的质量、惯量和网格几何存在差异。

因此，这不是单纯调整随机种子就能解决的问题。MuJoCo 官方文档也说明，严格数值复现依赖相同版本和完整的积分状态；接触过程会放大微小差异。

### 原因 2：历史演示缺少完整的控制器状态

原 HDF5 主要保存了物理状态、动作和观察，但没有保存当时完整的：

- 控制器目标和夹爪命令历史；
- 求解器内部积分状态；
- observable 缓存和采样时序；
- 演示被裁剪掉的前五步状态。

最新诊断发现，即使使用 MuJoCo 2.3.5，demo_2 不经过快照保存／恢复，直接从重建状态继续执行，仍出现约 0.03313 的误差。

这说明问题不只是当前快照序列化实现不完整。

更可能的解释是历史控制状态不完整、接触动力学敏感性及采集运行时差异共同作用，但现有证据还不能唯一确定各自贡献。

因此，继续寻找原始采集文件、尝试逐位复现所有历史轨迹，可能是一项成本很高而收益有限的工程工作。

## 三、这一步实验是否过于严苛？

我的判断是：存在两类过严条件，应当区别对待。

### 1. 历史轨迹误差必须小于 \\(10^{-5}\\)

对算法可行性验证：过严

这个条件适合证明历史回放具有数值一致性，但并不是 RCTR 必须满足的条件。

RCTR 真正需要的是：

\\[ \boxed{ \text{相同当前状态} \rightarrow \text{不同动作干预} \rightarrow \text{可重复的真实环境结果} } \\]

并不要求这个当前状态必须与数年前采集的某条演示轨迹逐元素一致。

如果我们能够在目前实际使用的 MuJoCo 3.2.3 环境中运行策略，保存完整状态快照，再从相同快照分别执行正常动作和干预动作，依然可以建立合法的反事实控制关系。

这实际上更符合 RCTR 希望解决的闭环问题。

但是我不建议直接把 \\(10^{-5}\\) 放宽成 \\(10^{-2}\\)。demo_2 的误差涉及接触和速度变化，简单放宽并不能证明其物理等价。

正确做法是改变需要验证的性质，而不是事后降低同一性质的验收标准。

### 2. 必须获得 3/3 成功、3/3 成功、0/3 失败

对探索性筛查：明显过严

原协议要求同一位置同时满足：

- 正常分支连续三次成功；
- 某个恢复候选连续三次成功；
- 某个失败候选连续三次失败；
- 至少两个不同演示满足全部条件。

这相当于要求在仅三个预选位置中，就找到多个几乎确定性的成功／失败控制关系。

即使一个候选动作真实成功概率达到 80%，在三次独立执行中全部成功的概率也只有 51.2%。两组都要求全成功，再加上另一个候选全失败，准入概率会进一步下降。

而且原协议只在动作第一维增加固定的 0.05 干预。如果该方向对当前控制阶段影响很小，或者所有候选都可以成功，算法根本得不到成功／失败对照。

没有找到 3/3 与 0/3 的极端对照，并不代表没有可学习的反馈控制规律。

这是一项筛查条件设置问题。不过由于此前没有启动任何策略分支，当前实验还不能用数据证明这一条件实际导致了假阴性。

## 四、我建议如何修正实验？

不再把历史演示精确复现当作反事实分支的前置条件。

改成一个独立、预先冻结的 RCTR Stage A2：当前执行状态的反事实可行性验证。

| 环节           | 原方案            | 修正方案                     |
| ------------ | -------------- | ------------------------ |
| 状态来源         | 原始 HDF5 中间状态   | 当前策略真实闭环运行产生的状态          |
| 状态恢复         | 需精确匹配历史演示      | 需精确恢复同一当前快照              |
| 动作干预         | 固定第一维 +0.05    | 预先定义多方向、小幅度且非零的物理干预      |
| 控制候选         | 固定 5 个 GMM 分量  | 保留 GMM 候选，并先确认实际动作差异     |
| 成功认证         | 一开始就要求 3/3、0/3 | 先统计配对成功差异，再独立重复认证        |
| 对 RA-Coreset | 使用选中演示的对应状态    | RA 继续承担原始记忆覆盖；新增状态记忆单独计费 |

新的关键流程是：

原 RA-Coreset Task6 父策略

在正式部署使用的仿真版本中执行

记录当前真实可达状态及完整八步历史

正常控制

原策略继续运行

动作干预

相同快照、匹配随机数

比较闭环成功／失败及后续恢复动作

筛查可学习的反馈关系，而非要求立即获得完美成功证书

这项修正有一个必须承认的代价：它产生的是新策略访问分布中的辅助数据，而不是严格复现旧演示的分支，因此会改变 RCTR 数据构造协议。

但原 RA-Coreset 的选样、buffer 和训练设置可以保持不变。只要单独报告新增仿真交互与记忆预算，并设置等预算的普通 BC 对照，仍然可以进行有意义的公平比较。

### 阶段 A2 应该怎样判定通过？

我建议分开两个门槛。

工程门槛仍然严格： 同一完整快照反复恢复后，相同动作和噪声必须产生一致的物理状态、原生观察和 GMM 执行行为。这个要求不应该放宽。

科学可行性门槛适当降低： 只要发现可重复、方向一致的干预／恢复效果，就可以认为值得进一步测试。所有候选的成败频率、干预幅度和跨状态覆盖都要完整报告。正式训练前再要求独立复核和预设的最低有效样本量，而不是从三个样本中强行寻找极端成功证书。

原 Stage A 的失败结果应保留为 `BLOCKED`，不能通过修改已冻结的阈值把它改写为通过。

## 五、最终评估

| 问题                    | 判断                           |
| --------------------- | ---------------------------- |
| 是否证明 RCTR 无效？         | 没有，算法尚未接受训练或闭环验证             |
| 状态恢复是否取得实质进展？         | 是，完整快照重复性和部分历史复现已通过          |
| 是否需要继续追求旧 HDF5 的逐位一致？ | 对历史复现研究需要；对 RCTR 可行性不必作为唯一前提 |
| 原 Stage A 是否过严？       | 是，探索性科学门槛明显偏保守               |
| 是否应直接进入完整训练？          | 不应，仍缺乏经过验证的可学习恢复关系           |
| 是否值得继续 RCTR？          | 值得做一次协议修正后的有限可行性实验           |

我的最终建议是停止继续深挖历史演示的精确重建，把资源转到基于当前闭环状态的反事实验证。

当前已经累计进行了 1195 个工程控制步，却仍然是 0 条正式反事实分支和 0 次训练。这说明研究正在被数据采集历史与仿真兼容性问题所主导，而不是在检验 RCTR 的核心假设。

下一步最有价值的不是降低误差阈值，也不是继续安装不同版本的 MuJoCo，而是用现有可精确重复的完整快照机制，在正式部署环境中构造少量真正可执行的正常／干预状态对，观察是否存在可复用的恢复行为。

如果这一步也无法得到足够的有意义监督，才应认真考虑放弃 RCTR；现在直接否定它，证据仍然不足。
