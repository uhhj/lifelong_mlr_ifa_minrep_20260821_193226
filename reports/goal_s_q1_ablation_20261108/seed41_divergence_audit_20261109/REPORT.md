# GOAL seed41：有效 q 同为 1 时的分歧定位

本次只读审计针对历史完整 S（2026-10-29）与新固定 q=1 的完整 S（2026-11-08），不是 Q 单候选方案。2026-11-09 实际 CPU 检查了两次运行的 8 个阶段 checkpoint、8 个缓存；另从已接受证据复算全部 400 轮与 6700 个门控块。新增训练、optimizer、模型前向和环境调用均为 0。原文件 SHA 在 CPU 审计前后完全不变。

**结论：seed41 的差距不能解释成支持度校准收益。两次所有实际保持阶段的有效 q 都为 1，但在线推理先出现浮点差异，进而产生不同的保持缓存；Task7 第一轮第 8 个门控块开始选择不同候选，后续训练轨迹分叉。已定位到推理输出、缓存和门控三个环节；尚不能把最初数值差异进一步唯一归因于某个 CUDA 算子、驱动版本或硬件故障。**

## 1. 两次是否真的都在用 q=1

逐项核验 `PROBES_7/8/9.json` 与实际 `support_memory.py`：

| 保持阶段 | 使用哪些旧任务 | 完整 S 的有效 q | 固定 q=1 的有效 q |
|---|---|---|---|
| Task7 | Task6 | 1 | 1 |
| Task8 | Task6、7 | 1、1 | 1、1 |
| Task9 | Task6、7、8 | 1、1、1 | 1、1、1 |

历史 S 的前三次采集均 10/10 成功。新运行前三次为 10/10、10/10、9/10，最后这个经验支持度 0.9 被固定 q=1 的定义覆盖；Task9 实际仍用 1。Task9 结束后的缓存不用于后续训练。

这里的 1 是任务支持度系数，并非整个保持项系数；两次全局 `lambda_R=0.1`、原四槽分母以及路由项系数均相同。但是 `q=1` 只保证乘数相同，不保证输入特征、teacher 均值/标准差、缓存窗口名单和归一化尺度相同。保持损失实际是模型与这些缓存内容共同决定的。

## 2. 最早可定位到 Task6 的在线采集，而非 Task7 的 q 修改

### Task6 训练本身相同

- 官方初始化模型和全部记录的 RNG 摘要逐项相同。
- 100 轮采样顺序、学习率、batch 数、累计更新、所有训练损失合计完全相同。
- 新读取两个 Task6 checkpoint，100 个 state_dict 张量全部逐位相同。
- 配对采集的初态文件、初态内容、Normal 噪声、环境种子、attempt 一致。
- `collect.py` 和 `evaluate.py` 解码后的文本及 AST 完全相同，差别仅源码文件换行格式。共享父项目的 236 项源码、6193 项文件绑定、数据阶段绑定、官方预训练模型均相同。

### 同模型、同完整输入，已保存的输出却出现微小差异

在 Task6 采集缓存中，初态编号 **21、23** 的 `step=6`（第 7 次策略动作，历史长度 7）保存了两边都能逐项对应的窗口：

| 实际 CPU 比较项 | 结果 |
|---|---|
| Task6 模型参数 | 全部精确相同 |
| 完整历史输入 feature | 14336 个元素全部精确相同 |
| 所选 GMM mode | 相同 |
| 输出均值 mu | 7 个元素中 5 个不同，最大绝对差 `1.1920928955078125e-7` |
| 输出标准差 sd | 7 个元素中 2 个不同，最大绝对差 `6.51925802230835e-9` |

这些值来自当时实际保存的 teacher 参数，不是本次重新做 GPU 推理得到的。它们在 `temporal_encode → policy_head.forward_fn` 之后、抽取 Normal 动作之前保存。此时尚没有保持损失，也尚没有本任务缓存归一化计算，因此 q、保持尺度和以后训练的门控都不能解释这两条推理输出的最初差别。

已保存的早期窗口在 step0/1/2/3/5 可精确相同；已保存特征最早在 **step7** 出现差异（初态 24，最大差约 `5.01e-4`）。这里必须区分两件事：**step6 是现存配对窗口能证明的最早策略输出分歧；缓存是 reservoir 抽样，并非完整逐步记录，不能据此证明所有轨迹在更早步骤绝无其他分歧。** 不同轨迹的两个时间点也不构成单条轨迹的逐步因果证明。

随后 10 条完整动作流的 SHA 全部不同。两边最终都成功 10 次，但其中 6 条轨迹的成功终止步数不同，例如初态 22 为新运行 80 步、历史 S 88 步。“10 次都成功”远不足以证明采集轨迹相同。

## 3. Task7 开始时，保持缓存已经不是同一个训练输入

Task6 缓存两边各 128 个窗口：

- `(trajectory, step)` 相同的窗口只有 124 个；各有 4 个独有窗口。
- 124 个同位置窗口中，109 个 feature 不同，108 个 teacher mu 不同，108 个 teacher sd 不同。
- 同位置 feature 相同但 teacher 输出不同的两个窗口，就是上面的 step6 证据。
- Task6 第一个归一化尺度也相差 1 个 float32 ULP：历史 S `0.43576446175575256`，新运行 `0.43576449155807495`，差 `2.9802322387695312e-8`。该尺度由 CPU 对固定训练动作计算；这是另一个数值执行差异，不能统称 GPU 造成，也不是最初在线输出差异的原因。

Task7 的新任务 probe 索引和旧缓存 probe 数字索引相同，但旧缓存内容不同；数字索引相同不等于取到相同 feature/teacher。更晚 Task8、9 还叠加了已分叉的模型与各自采集数据。

这不是发现“缓存文件损坏”：两个缓存各自通过原验收，而且此次 SHA 与接受时一致。问题是两次独立在线采集得到了不同的、各自有效的缓存，因而不再是同输入的受控比较。

## 4. Task7 第 8 个块首次选了不同分支

Task7 第一个块开始，C 候选在新任务上的 BC/执行 probe 两边精确相同，而旧任务保持 probe 已不同；Q 候选的新任务和保持 probe 也开始不同。前 7 个块两次都选 C。

**第一处分支选择不一致：Task7，第 1 轮，batch=70，块序号 8，累计接受更新 10070→10080。**

此块的 C 新任务 probe 在两次运行中仍完全一致。以下是 `Q - C` 的实际值：

| 门控比较 | 新固定 q=1 | 历史完整 S |
|---|---:|---:|
| BC 差值，要求 ≤0 | −1.437962e−6 | +2.639741e−5 |
| 执行 probe 差值，要求 ≤0 | −3.725290e−8 | +6.034970e−6 |
| 保持 probe 是否改善 | 是 | 是 |
| 最终选择 | Q | C |

协议采用零 epsilon。很小的新任务 probe 差异足以改变通过/拒绝判定；因此它会把数值/缓存变化转成不同的接受路径。这里没有修改阈值，也没有据此选择新阈值。下一块（batch=80）的 C 新任务 probe 首次也不同，说明两边继续从不同路径推进。

“前 7 块 C 的 probe 相同”是标量证据，不是保存了每块完整状态并验证逐位相同；不要把它扩大成未记录的状态证明。阶段末完整 checkpoint 的比较则是本次直接读取核验的：

| 阶段末 | 不同 state_dict 张量/100 | 张量元素最大绝对差 | 本阶段不同门控决定 |
|---|---:|---:|---:|
| Task6 | 0 | 0 | 无门控 |
| Task7 | 88 | 0.07954 | 584/1400 |
| Task8 | 88 | 0.27874 | 857/1900 |
| Task9 | 88 | 0.43863 | 1491/3400 |

共 2932/6700 个块决定不同。该比例是路径分歧描述，不是性能差距的因果贡献率。

## 5. 代码、缓存、硬件分别能判定到什么程度

**科学配置或误写 q：未发现这类错误。** 两次有效 q、lambda_R、四槽分母、损失定义、候选步骤、采样顺序和学习率一致。`losses.py / legacy_losses.py / memory.py / legacy_memory.py / updates.py / legacy_updates.py / candidate.py / collect.py / evaluate.py` 等文本与 AST 相同。固定 q 的变化只有 `support_memory.weights` 对非空缓存返回 1，在 seed41 的实际保持权重上与旧 S 等价。其它变动是同值参数引用、计数/元数据/准入检查、硬件比较和环境锁调度。

**工程代码并非逐字完全相同。** 新运行另用了设备内状态快照、合并有限值判断和一致性检查优化，拥有既有完整路径验证及本次各阶段 `COPY_EQ/BRANCH_COPY_EQ/CHECK_EQ` 证据。这些证明有其验证范围，不能宣称覆盖所有跨硬件在线计算。但 `train_wrapper.py` 只在训练解释器中修改训练函数；在线采集是新子解释器直接执行相同 `collect.py`，且进入采集前 Task6 模型已经精确一致。所以未发现这些训练优化造成最初 step6 在线输出分歧的证据。

**缓存差异：直接证实，而且发生在训练分叉之前。** 它改变保持损失输入和门控旧任务 probe，是后续分叉的明确通道。未做交换缓存反事实更新，所以不声称已量化其独立贡献，也不排除后续 GPU 数值差异继续参与。

**硬件/数值后端：最符合现有证据，但不等于 GPU 坏了。** 历史设备为 RTX 4080 SUPER（能力 8.9），新设备为 RTX 3090（8.6）。记录的 PyTorch 1.13.0+cu116、CUDA 11.6、cuDNN 8302、matmul TF32=false、cuDNN TF32=true 相同。已经存在“同模型、同单样本完整输入、同 mode、不同在线输出”的直接证据，因而首先应定位到在线策略的数值执行层，而不是 q 或任务初态。当前保存物不足以进一步区分具体 GPU 内核、底层库/CPU执行环境变化、驱动或调度影响；也未保存完整原始图像、仿真状态和逐算子跟踪，无法完整拆开后续渲染/动力学累积差异。

事后出现的 `nvidia-smi` 驱动连接错误没有训练期间的发生时间证据，不能用来解释此次结果，也不能据此判定当时 GPU 故障。此次没有重启服务器或更改驱动。

## 6. 指标在哪个阶段体现，以及应怎样解释

以下是全部已完成正式评估的成功率（每单元 20 个配对回合），顺序均为“历史 S / 固定 q=1”：

| 训练到 | 测试 Task6 | Task7 | Task8 | Task9 |
|---|---:|---:|---:|---:|
| Task6 | 90 / 85 | — | — | — |
| Task7 | 70 / 70 | 100 / 100 | — | — |
| Task8 | 65 / 60 | 100 / 100 | 95 / 80 | — |
| Task9 | 65 / 30 | 100 / 100 | 85 / 85 | 80 / 45 |

Task6 正式评估是在全部训练后进行的，但它使用相同 Task6 模型，也已出现 90% vs 85%，进一步说明评估执行路径存在差异。Task7 末模型虽已不同，两个成功率恰好相同；不能据此把训练分叉推迟到 Task8。最终 82.5% vs 65% 的 17.5pp 差距来自 Task6、Task9 各少 7/20 次成功，Task7、8 最终相同。

**这对 seed41 应视为相同有效支持权重下、执行条件和在线缓存不同的两条训练轨迹，不能作为“去掉支持度校准造成 17.5pp 下降”的证据。** 这也要求三 seed 的总体均值差保留执行/硬件混杂说明，而不是把全部差距归因于校准。既有指标与预算接受状态不作废，但“程序按各自协议完成”与“支持度单因素因果得到验证”是两件事。

本次没有为改善结果重跑、补采、重评，也没有调 epsilon。至此已定位现有证据能支持的最早分歧、传播链和归因边界。
