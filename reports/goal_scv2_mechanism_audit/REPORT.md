# SC-v2少量换样为何仍伴随Task6、9下降：只读机制审计

2026-10-18，GOAL seed42，原Coreset对比已完成SC-v2。只读取既有checkpoint、RNG快照、存储清单、特征、训练曲线和episode记录；CPU张量比较、原距离计算和索引顺序重建；**0模型前向、0优化器更新、0环境调用、0新增闭环**。旧实验与固定停止决定不变。

## 结论

本轮最重要的新发现是：**只更换少量集合成员，仍会通过文件排序改变大量旧样本进入更新步骤的位置。** Task9只换11个旧成员，但810个共同旧样本发生位置迁移，按实际冻结加载器与采样器重建，100轮中31,696/33,700个batch的样本集合不同，占94.05%。这并非增加回放或改变组批算法，而是同一算法处理新成员集合的自然结果。

此外，Task9训练继承的stage8模型已经不同，进入Task9评估时CUDA RNG也已不同。因此当前可以定位到“记忆成员/旧样本重排→连续优化路径改变”和“前序评估耗时→后序动作随机流偏移”两个真实通道；**不能仅凭现有日志给两者分配性能损失比例，更不能证明具体哪11个样本造成了下降。**

几何底线确实守住，SC-v1的终点堆积问题也没有复现。不能沿用上一轮的“补了太多终点、破坏覆盖”解释SC-v2。新的证据指向：修复目标改善很小，但训练与评估轨迹可以产生远大于成员数量比例的变化。

## 1. 少量换样没有限制实际batch的变化范围

冻结源码`libero/lifelong/algos/mlr.py::build_dataset_for_task`先对buffer路径按字符串排序，再把旧buffer与当前完整数据拼接，使用独立`random.Random(42).shuffle`；随后`DistributedSampler(seed=0)`按epoch打乱索引。SC-v2虽然在选择清单中保留原位置并替换槽位，但真实训练按新文件名重新排序，不使用清单的原位置作为dataset位置。

一个旧文件被移出、另一个不同文件名加入，会使两个字典序位置之间的一串共同文件改变排名。相同shuffle索引作用在不同身份排列上，共同旧样本就会落入不同更新步。

|训练阶段|累计新旧成员差异|共同旧样本位置迁移|对齐后身份不同的dataset槽位|100轮不同batch数/总数|比例|
|---|---:|---:|---:|---:|---:|
|Task6|0|0|0|0/10,000|0%|
|Task7|5|242|247|11,889/13,900|85.53%|
|Task8|7|600|607|18,179/18,500|98.26%|
|Task9|11|810|821|31,696/33,700|94.05%|

这些是**由冻结函数AST、真实存储清单和目标端PyTorch1.13 DistributedSampler确定性重建的索引统计**，不是训练时保存的逐batch日志。重建没有加载训练payload或调用DataLoader迭代、优化器。原当前任务样本顺序和位置完全一致，每个位置的任务ID也完全一致；改变的是旧任务内部成员身份及排序。因此不能说“Task9自己的新数据被重新排序”或“新旧任务比例改变”。

Task9仍是1,969条完整当前数据+1,396条旧记忆，11个成员占全训练集0.3269%、占旧记忆0.7880%。但当前数据的196,900次样本曝光中，181,464次（92.16%）处在旧样本组合发生变化的batch里。这里的“受影响batch”只是内容不相同，**不是梯度一定显著变化，更不是94%的更新变坏**。现有数据没有隔离“成员内容”与“共同旧样本顺序”的独立贡献。

同一套顺序更新、AdamW状态、共享网络会沿不同batch序列累计变化；100轮中每个新成员都反复出现。有限交换数没有约束梯度相近、参数相近或策略输出相近。

## 2. 模型在Task9之前就已经分叉

对实际state_dict张量比较，排除固定注意力mask等buffer后统计参数距离，而非比较包含路径的整个checkpoint文件哈希。

|阶段最终模型|不同张量键/100|时间Transformer相对L2差|策略头共享层相对L2差|
|---|---:|---:|---:|
|6|0|0|0|
|7|87|0.18988|0.25315|
|8|87|0.31426|0.42957|
|9|87|0.53360|0.67373|

相对L2定义为两模型参数差范数除以原Coreset参数范数，只是描述性尺度，不能转换为行为损失比例。Task6所有张量、初始化RNG、100轮loss都相同；差异在第一次入库后、Task7训练中出现。Task9的起点并非同一stage8网络，随后又经历不同的旧样本混合更新。

Task9训练仍完成100轮、33,700步，学习率及总步数逐epoch一致，没有训练中断、预算缩水、loss非有限或配置漂移证据。Task9末轮混合训练loss为原−30.42062、SC-v2−30.43985；末10轮均值−29.93192、−29.92228，十分接近。日志没有独立Task9 loss，也没有共同验证集，因此既不能由这些值证明Task9拟合更差，也不能用近似loss排除控制性能下降。GMM密度的负对数似然为负本身不是错误。

## 3. “覆盖没损害”需要限定为两项全局统计

SC-v2守住最大最近距离和平均最近距离；复算没有发现实现违反底线。但两项聚合统计并非逐点保护。复用原全部任务标定尺度和原Distance函数，不重标定、不重新选样，得到：

|任务|最近距离变大窗口|变小窗口|不变窗口|变大者中原被移出中心|非移出中心变大数|
|---|---:|---:|---:|---:|---:|
|6|6|27|964|5|1|
|7|2|2|885|2|0|
|8|6|7|891|4|2|

Task6移出的`210.pt`原先自身就是中心、距离为0，删除后最近距离约0.27624，仍低于原全局最大0.27877，所以合法。其余点的改善足以让平均值下降。Task7两次交换使两个中心的零距离与两个新中心互换，全局平均恰好不变。

这不构成大范围覆盖崩塌：Task6除移出中心之外只有一个点距离增加0.01213，Task8只有两个点变差。不能把少量局部退化直接判定为闭环失败原因；日志没有失败轨迹可以把这些位置与失败状态关联。

原距离只使用两个视觉token的8步余弦差和末端动作距离；不直接包含状态token、当前可训练时间网络的敏感性、BC梯度或未来闭环访问分布。因此即使逐点距离都不错，也没有“重训后成功率不降低”的保证。覆盖约束仅限制已记录示范特征空间的取舍。

## 4. Task6原偏差只得到很小修复

Task6正夹爪命令比例：原Coreset54.7094%，SC-v2为54.1082%；不同真实监督时刻总体参考为44.5523%（原完整窗口口径41.4243%）。指定联合构成E从0.102466降至0.096454，偏差仍大量存在。

Task6只加入5个不同监督时刻，移出5个，独立监督数量仍495；终点窗口仍14。移出的5条都是正命令，补入2正3负，净只减少3条正命令。移出窗口的末端平移指令范数均值0.13783，加入为0.44568；其中接近零平移（范数<0.01）由2条换成1条。它表明“修正命令符号/时间构成”同时改变了具体控制内容，**不能把低幅值自动解释为关键稳定阶段或证明丢失了抓持能力**。

Task6最终成功率45%→30%，同20初态配对为SS=2、SF=7、FS=4、FF=7，共11条结果翻转、净少3条成功；并非只少了固定3条。Task6是stage首个评估任务，四类起始RNG相同，两向量均600步，因此没有后序Task8/9已经确认的前序CUDA偏移这一混杂。它更直接地提示模型执行表现改变，但仍不能排除环境数值执行差异，不能从单seed20条推断普遍因果。

## 5. Task9下降的来源：哪些已排除，哪些有证据

Task9是`put_the_wine_bottle_on_the_rack`，本轮初学即最终模型，90%→50%属于新任务学习/执行表现下降，不是继续训练后的Task9遗忘。

**已排除的直接解释：**

- Task9自己的6条存储交换发生在Task9训练和最终checkpoint保存之后，没有后续训练使用它。
- Task9原Coreset与SC-v2的IFA任务对都为空，`angular_mean`返回精确零项，Task9没有新增的直接IFA梯度约束。
- Task9当前1,969条窗口、当前样本位置、任务槽位、337步/epoch、100epoch和学习率轨迹保持一致。
- 没有SC-v1式的终点堆积：Task9混合训练集合的终点窗口比例两组都是4.0119%；正命令比例仅46.0624%→46.0030%，没有明显总体符号频率重分配。
- resolved评估配置差异仅为路径、合同和不参与前向的selector标签；初态、模型阶段及模态绑定一致。

**存在直接证据的通道：**

1. 前面Task7/8已经形成不同共享模型；Task9从这些不同模型出发。
2. 旧样本排序放大了实际混合batch差异；任务间比例不变不等于训练梯度序列相同。
3. 最终Task8由60%提升到80%，Task9由90%下降到50%，与任务间取舍相容；但没有梯度或隔离干预，不能声称“已证明Task8挤占了Task9容量”。
4. Task9的实际动作随机流起点不同，需与模型差异同时考虑。

此前Task7仍选(6,7)、Task8仍选(6,8)，任务对没有变化；但记忆内容与学习表示变化，早期IFA间接作用没有被隔离。不能将“任务对相同”扩大为“IFA全过程完全相同”。

## 6. Task9动作RNG偏移已核实，不只是可能性

读CPU加载的既有RNG快照内容，Python/NumPy/CPU Torch在每个cell前都一致；CUDA在stage8/task8、stage9/task8、stage9/task9不一致。

|待评单元|此前累计向量步：原/SC-v2|CUDA起点一致？|
|---|---:|---|
|stage9 / Task6|0 / 0|是|
|stage9 / Task7|1200 / 1200|是|
|stage9 / Task8|1367 / 1365|否|
|stage9 / Task9|2567 / 2565|否|

stage9 Task7两组都是20/20，但原两批结束于84、83步，SC-v2为81、84步，累计少2步。代码只每stage重置CUDA随机状态；后续Task8两组均600+600步，差异被带入Task9。Normal动作采样是在GPU上消耗全局随机流，**少2步不是只影响后面两个动作，而是后续抽样序列的起点改变**。这证明实际随机条件未被逐轨迹匹配；并不证明偏移足以造成40pp下降。

Task9下降也没有像SC-v1那样只集中在第二个向量：

|初态索引|原Coreset成功|SC-v2成功|净差|
|---|---:|---:|---:|
|0–9|8/10|4/10|−4|
|10–19|10/10|6/10|−4|

总体SS=9、SF=9、FS=1、FF=1。原成功转失败的索引为0、1、4、7、8、10、12、13、14；原失败转成功为5。原第一向量600步、第二向量217步；SC-v2两向量均600步。组步数不能当作各episode成功时间。

本轮没有逐步机器人状态、动作、视频或独立逐轨迹RNG日志，所以不能判定是抓取、放置、碰撞还是其他执行失败。也没有“固定同一模型、交换两种随机流”的既有结果，不能把9条新增失败全部归于随机性或全部归于模型。

## 7. 本轮结论的边界

最强的结论是：**SC-v2实现了预定的几何/构成约束，但这些约束没有保护优化轨迹。少量换样经过路径排序后改变大量混合更新，模型差异早于Task9出现；Task9评估另有已证实的动作随机流差异。**

对Task6，修复幅度很小，原构成偏差基本仍在，而模型训练路径已经改变。对Task9，主因候选应放在“此前共享模型+当前旧样本混合更新+实际评估噪声”，不是Task9最后入库，也不是Task9直接IFA约束。现有数据无法进一步给出可识别的因果比例。

维持未通过AUC扩展门槛、不扩43/44的结论。未追加训练、闭环、梯度测量、模型前向或新超参数方案；不将失败初态用于选样。
